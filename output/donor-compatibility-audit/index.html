04 / Small, owned changes

Extend shared contracts.
Keep donor-specific ownership.

Some gaps are small defects; others need a new permission or delivery contract. A broad “make every module generic” refactor would mix these responsibilities.

Recommended boundaries

No universal record layer

One workflow capability contract

Reuse the subject registry, canonical validator, and donor permissions for manual creation, templates, and AI. Carry subtype in schema, storage, versions, publishing, and export/import.

Narrow transaction-safe events

Repair Meta/hosted/CSV creation dispatch at their transaction boundary. Emit applied-stage conversions inside donor status changes. Occurrence and action receipts must be atomic with effects.

Contact identity separate from message access

Reuse transport, consent, sender, sending-hours, and provider reconciliation. Add donor association and per-message record-context authorization; do not expose whole shared conversations.

One hosted/embed tracking-policy resolver

Unify mode, consent, event identity, and destination admission. Keep embedded lead capture distinct from a full hosted application. No new browser Pixel is assumed.

Donor-owned operational imports

Reuse parsing/transforms/approval patterns, not surrogate-bound import tables and executors. Add subtype-scoped batch/row outcomes and encrypted retained uploads.

Separate onboarding from preservation.

→

Operational CSV

Create-only intake with validation, duplicate review, atomic row outcomes, and retry. No restore IDs, history, SSNs, or inferred consent.

Privileged profile package

Preserve stored fields, explicit clears, form snapshots, provenance, and photo/history manifest. Recommend read/verify-only first; full restoration is a separate scope decision.

W0

Repair defects and preserve donor intent

Start here

Deliver

  • Fix email preview totals and Zapier test response donor_id.
  • Keep Meta source canonical; flag incompatible source mappings for repair.
  • Preserve exact subject across template save/use/publish/version/export; use canonical validation and permissions.
  • Disable ambiguous legacy donor-intent artifacts for explicit repair; never guess the subtype.

Exit checks

  • 100 eligible / 50 sampled still reports 100 eligible and 0 suppressed.
  • Egg template → egg workflow; sperm template → sperm workflow. Wrong pipeline and denied user fail.
  • Zapier donor test response retains its donor ID; source mapping behavior is unambiguous.
Migration and compatibility impact

Add/backfill template subject metadata across relevant artifacts. Existing surrogate templates remain surrogate; ambiguous donor intent must not silently become enabled surrogate automation. Synchronize backend/frontend contracts through existing generators where applicable.

W1

Make intake and conversion occurrences recoverable

Depends on subject contract

Deliver

  • Commit donor creation and its job atomically for Meta conversion, hosted promotion, and new CSV processing.
  • Keep ordinary donor CRUD workflows synchronous.
  • Add occurrence dedupe, per-action transactional receipts, and email admission idempotency.
  • Record conversion occurrences in donor_service.apply_status_change, not when approval is requested.

Exit checks

  • Crash after commit, replay, mid-action retry, and lost worker claim do not lose or duplicate effects.
  • Pending stage requests emit nothing; undo emits nothing; repeated buckets dedupe.
  • Each new job has safe-replay proof, stale-claim classification, and quarantine alerts/runbook.
Rollout constraint

Deploy consumers before producers. A queued event is not “durable end-to-end” until retry classification and action-level idempotency are proven. Preserve existing surrogate event identities and workflow-action stage reporting.

W2

Extend five independently owned foundations

Parallel where independent

Deliver

  • Imports: subtype-fixed upload → map → validate → approve → queued execution → row outcomes/retry; create-only, duplicate skip/review, encrypted upload expiry. Scope templates/learning by entity and subtype.
  • Privacy: contact association and purpose-specific consent; per-message record context filters bodies, media, previews, counts, and unread state before pagination.
  • Operations: permission-based donor/correspondence access; activate existing appointment/match capabilities without broad Tickets access.
  • AI: donor-aware generation and bounded, cache-off donor chat. Saved workflows stay disabled.
  • Tracking: shared hosted/embed policy, consent checks, deterministic event IDs, exact pipeline mapping, and internal-only behavior.

Exit checks

  • Imports cannot merge/overwrite existing records, infer consent, or trigger unreviewed outreach. Retry does not duplicate rows; lease heartbeat survives large batches.
  • Shared-phone donor access cannot read surrogate messages or leak their counts/previews. STOP is global; phone edits do not retarget jobs.
  • AI history, streaming, context, and targets recheck record/capability permissions. No unnecessary sensitive context.
  • internal_only emits no external request. Retire or consume queued tracking modes explicitly; do not replay a historical backlog.
Data and scope choices

Add donor import batch/row records and donor contact/context associations. Existing import templates backfill as surrogate, not donor. Build a privileged read/verify-only profile package with explicit-clear and form-derived reconstruction tests; lossless restoration needs a separate privileged restore slice. Embedded full-application/file-upload support is not assumed by tracking parity.

W3

Enable donor messaging and reviewed actions

After privacy, identity, templates, durability

Deliver

  • Donor SMS workflow actions and promotional campaigns through the existing org-owned sender/delivery engine.
  • Published templates, purpose-specific consent, execution-time audience, and subtype/stage filters.
  • Freeze recipient/context/content at delivery materialization, not campaign preview; recheck STOP/archive/consent before send.
  • Reviewed donor email compose/reply with atomic ticket + record link; AI proposals for notes/tasks/assignment/stage/email.

Exit checks

  • Queue delays, retries, archived donors, edited phone numbers, STOP, and changed consent cannot deliver to the wrong identity.
  • One shared contact gets at most one eligible campaign delivery; ambiguous personalization is skipped.
  • Published content versions, sending hours, provider-ambiguity reconciliation, and human review are preserved.
Do not reinterpret campaign snapshots

Snapshot approved filters, template version, and settings. Preview is an estimate; the execution resolves the audience. Freeze a delivery’s recipient and content once materialized, then preserve it across retries. Do not freeze the whole recipient list at launch.

W4

Add the genuinely new shared SMS features

Not merely donor parity

Deliver

  • Appointment SMS confirmations, reminders, cancellations, and reschedules with explicit recipient/template and occurrence version.
  • AI SMS drafting with mandatory human review.

Exit checks

  • Reschedule/cancel invalidates stale reminders; retried jobs and uncertain provider results do not resend.
  • AI cannot send externally without review or bypass consent and delivery admission.
Dependency distinction

Appointment email already exists. Appointment SMS and AI SMS are separately budgeted shared extensions, not prerequisites to basic donor SMS workflows or promotional campaigns.

W5

Authorize destinations and roll out by capability

External approval required

Deliver

  • Document permissible event purpose, criteria, payload, destination, and provider restrictions.
  • Run explicitly authorized provider tests; verify direct Meta OR Zapier route per destination.
  • Deploy consumers first, stop-admission controls, sanitized monitoring, and actionable retry/quarantine handling.

Exit checks

  • Full affected suites, tenant/role/CSRF negatives, both subtypes, migrations, provider ambiguity, retention/holds, and relevant browser behavior.
  • Rollback stops new admission without replaying accepted sends. No production migration or activation without authorization.
A gate can mean “do not activate”

Donor-related context can be sensitive even if the event is called “Lead.” Renaming, hashing, or consent does not override Meta’s restrictions. If no admissible event exists, keep that destination off and retain internal reporting. Non-Meta Zapier destinations need their own disclosure review.

06 / Evidence, verification, and release boundaries

Built does not mean
authorized to send.

These are implementation acceptance criteria and activation gates. The audit did not run provider tests, inspect production data/configuration, or certify current compliance.

Decisions to preserve

Default external activation off

Meta and other external destinations

Validate both event names and criteria/context. Donor intake can imply reproductive health. No sensitive-event delivery by relabeling it “Lead,” hashing identifiers, or relying on consent alone. Review Zapier disclosures per destination, including non-Meta destinations.

Meta event restrictions ↗ · Meta technology terms ↗

Correct “internal only” explicitly

This changes existing shared tracking behavior. Require settings/admin reconfiguration, a single hosted/embed resolver, consent gates at event creation and dispatch, and no historical backlog replay.

Prove safe replay before activation

Occurrence dedupe alone is insufficient. Persist side-effect receipts atomically, retain provider ambiguity fences, and classify each new job before allowing automatic stale-claim retries.

Keep sensitive context bounded

Donor chat starts cache-off. Do not include SSNs, unnecessary health/partner fields, unrelated match data, or shared-phone correspondence. Recheck permissions when viewing history and executing proposals.

Acceptance test matrix

Subtype isolation

Egg and sperm stages, templates, recipients, and imports cannot cross silently.

Tenant + role + CSRF

Cross-org IDs, denied permissions, cookies without CSRF, and public-token scope fail closed.

Shared contact privacy

Messages, media, counts, unread, and preview text exclude unrelated record context.

Crash + retry

Post-commit failure, duplicate delivery, stale leases, partial action loops, and ambiguous outcomes.

Approval + consent

Review revoked, donor archived, number changed, STOP received, and content/template updated.

Data preservation

Explicit clears, form fallback, schema/mapping snapshots, photo/history manifest, retention/holds.

Tracking contract

No external internal-only calls, stable IDs, one route, no request/undo stage events.

Operational usability

Loading/error/empty/populated behavior for affected features; import retry and permission-denied flows.

Planned verification: focused regressions during each slice; Ruff/type/lint checks; full affected suites for shared changes; migration and negative tests before rollout. None of these future feature tests are claimed as passing by this report.

Fable review refinements incorporated

Review thread ↗
  1. AI cache off initially: existing summary identity is not permission-sensitive.
  2. Applied-stage injection point: donor status service covers approved changes; undo must not create a conversion.
  3. Profile package scope: read/verify-only is the bounded recommendation; restoration is an explicit additional slice.
  4. Appointment SMS is new shared work: it is not an existing surrogate feature to “turn on” for donors.
  5. Preserve surrogate conversion semantics: donor stage-apply provenance differs from the existing surrogate workflow action and must be visible in mapping/tests/monitoring.
