Recommended decision

Choose Plan B: a modular policy kernel and custom roles, delivered incrementally inside the existing stack.

Keep Google/OIDC authentication, PostgreSQL, authenticated membership-derived tenant scope, CSRF enforcement, and the SQLAlchemy organization backstop. Replace scattered role and permission branches with one typed authorization decision service shared by API dependencies and a generated frontend capability manifest.

Add organization module entitlements, code-owned capability definitions, organization-defined roles, and explicit record-scope policies. Treat access as an intersection, so enabling a module never grants a person access by itself.

Sequence: ship Plan A’s consolidation work first, continue into Plan B’s data model, and adopt Plan C only when object-level sharing or multiple services make a network authorization plane worth its operational cost.
  • Expected delivery8–12 weeks in five reversible phases
  • Primary payoffOne place to toggle modules, roles, actions, and frontend surfaces
  • Primary trade-offModerate schema and migration work before custom roles are useful
  • External serviceNot required for the recommended target
  • Identity scopePrepare for multi-organization membership; do not enable it without a confirmed use case and tenant-switch threat model

Keep / identity
External identities are already separate from users.

AuthIdentity binds provider subject to a global User; session records support revocation; MFA state is enforced centrally.

Constraint / identity
Membership enforces one organization per user.

Membership.user_id is unique and the session carries one organization and one fixed role. This is simple and safe, but it is a future limit for consultants, shared staff, or agency groups.

Keep / tenancy
Tenant isolation is derived from authenticated membership.

The API validates organization host, stamps the request session, and applies a SQLAlchemy organization-scoping backstop to top-level ORM reads. This must remain outside tenant-configurable permissions.

Keep / authorization
Role defaults, organization overrides, and member grants/revokes are audited.

Backend dependencies deny missing permissions, developer-only capabilities are filtered for non-developers, and permission changes are evaluated from the database on protected API calls.

Gap / modules
There is no platform-wide module entitlement model.

ai_enabled and feature-specific settings exist, but product modules, permissions, navigation, route loading, API access, and record scope are not represented by one contract.

Gap / frontend
Capability decisions are reconstructed across pages and components.

The sidebar and feature pages mix permission strings, role shortcuts, organization flags, and local special cases. UI visibility can lag changes and is difficult to audit as a whole.

02 / Problem model

“Can this user do this?” currently crosses four different concerns.

Identity
Who is signed in?

User, provider subject, MFA, active session.

Tenant
Which organization?

Membership, host, session organization, database scope.

→
Availability
Does the organization have the module?

AI and several integrations have bespoke enablement flags; most product modules do not.

Capability
May this member perform the action?

Fixed role defaults + organization role overrides + member grants/revokes.

Record scope
May they act on this resource?

Ownership, queue, intake-pool grant, stage, author, or platform-admin logic.

→
API enforcement
FastAPI dependency + service policy

The authoritative boundary.

Frontend projection
Navigation + routes + actions + queries

Must mirror decisions without becoming a security boundary.

ALLOW = authenticated ∩ active_membership ∩ tenant_match ∩ module_enabled ∩ capability_granted ∩ resource_policy_passed ∩ safety_constraint_passed
Drift risk

Adding a capability can require edits to the enum, registry, role defaults, policy map, backend dependencies, frontend strings, navigation, page guards, and tests.

Toggle ambiguity

A module switch, a role permission, and an ownership rule are different controls. Treating them as one checkbox can either over-grant access or create confusing partial enablement.

Role rigidity

Four fixed roles encode job titles and privileges together. Agency-specific roles such as auditor, coordinator, finance, or read-only reviewer become collections of individual exceptions.

03 / Options

Three viable plans, from consolidation to an external decision plane.

Plan A / Lowest change
Consolidate the current RBAC system
Time4–6 weeks
RiskLow
SchemaSmall or none
Best whenThe four roles remain sufficient

Build

  • One typed capability catalog with module, resource, action, label, risk tier, and dependencies.
  • Generated TypeScript capability keys and a declarative frontend surface manifest.
  • useAuthorization(), <Can>, route guards, and query enablement from one snapshot.
  • Backend lint/test inventory that maps every protected route to a policy.

Gain

  • Far fewer string checks and sidebar exceptions.
  • One review surface for API and UI coverage.
  • No new runtime dependency or major data migration.
  • Immediate base for safer module toggles.

Limit

  • Roles stay fixed and organization-specific job design still creates overrides.
  • Record-level policies remain distributed unless explicitly migrated.
  • Single-organization identity remains unchanged.
  • Improves implementation modularity more than business configurability.
Plan B / Recommended
Add a modular policy kernel and custom roles
Time8–12 weeks
RiskMedium
SchemaRole, assignment, module, and version tables
Best whenAgencies need different access packages

Build

  • Code-owned capability catalog and organization-owned role definitions.
  • Many-to-many member role assignments with built-in roles retained as seeded templates.
  • Organization module entitlements independent from member permissions.
  • A policy kernel accepting principal, action, resource, and context, with typed reason codes.
  • An authorization snapshot/version consumed by the frontend.

Gain

  • Admin-friendly module and role toggles without code changes for every agency variation.
  • Resource policies become testable named rules instead of inline role branches.
  • Frontend visibility, route loading, and API enforcement share one vocabulary.
  • Preserves current deployment topology and low-latency database checks.

Trade-off

  • Requires dual-read migration and a compatibility adapter for the four current roles.
  • Multiple roles need explicit conflict rules; deny must win.
  • Admin UI needs impact previews and lockout protection.
  • Multi-organization membership should remain dormant until product demand justifies tenant switching.
Plan C / Highest flexibility
Externalize authorization decisions
Time12–20+ weeks
RiskHigh
RuntimeNew policy service or managed dependency
Best whenObject sharing and multiple services are core

Build

  • OpenFGA for organization, team, case, queue, and object relationships; or Cedar/OPA for rich contextual rules.
  • Policy model/schema versioning, relationship synchronization, decision telemetry, and consistency strategy.
  • Local enforcement adapters so routers never call a vendor SDK directly.
  • Shadow evaluation against the current system before cutover.

Gain

  • Strong fit for delegated and object-specific access across services.
  • Policy lifecycle, testing, and relationship queries become first-class.
  • New services can share one decision vocabulary.
  • Supports future machine or agent principals cleanly.

Trade-off

  • Authorization enters the request availability and latency path.
  • Data synchronization, cache consistency, outages, and policy deployment become operating concerns.
  • Tenant isolation still belongs in application and database boundaries.
  • Excessive for current fixed-tenant, mostly organization-level access patterns.

05 / Recommended target

A layered decision contract keeps toggles useful without weakening tenant or record boundaries.

Layer 1

Authentication

User, AuthIdentity, MFA, session revocation. Identity proves the principal; it does not grant domain access.

Layer 2

Tenant context

Active Membership derives organization scope. Host validation and database backstop remain fail-closed and non-configurable.

Layer 3

Module entitlement

OrganizationModule decides whether the agency has Surrogates, Donors, Tickets, AI, Reports, or another module.

Layer 4

Role capabilities

Built-in or custom AuthorizationRole assignments grant code-defined actions. Member denies override all grants.

Layer 5

Resource policy

Named rules evaluate ownership, queue membership, pool grants, stage, authorship, and organization-bound relationships.

Decision point

AuthorizationService.decide()

Input: principal, action, optional resource, context. Output: allow/deny, stable reason code, policy version, and non-sensitive audit metadata.

API enforcement

Typed dependencies

require_action(Action.SURROGATE_EDIT) handles coarse checks; services call the same decision boundary for loaded resources.

Frontend projection

Authorization snapshot

One bootstrap supplies modules, capabilities, reason-safe flags, and version. A route/surface manifest controls navigation, prefetch, pages, and actions.

07 / Migration sequence

Dual evaluation makes the upgrade reversible and exposes policy mismatches before enforcement changes.

Phase 0

Freeze the vocabulary

  • Inventory every API route, page, navigation item, query, and action.
  • Classify each rule as tenant, module, capability, resource scope, or safety constraint.
  • Record current allowed/denied fixtures for all four roles.
1 week
Phase 1

Unify contracts

  • Add structured capability metadata and generate TypeScript keys.
  • Create the frontend surface manifest and useAuthorization().
  • Return stable 403 reason codes and authorization version.
2 weeks
Phase 2

Introduce the kernel

  • Wrap existing permission resolution in decide().
  • Move inline resource checks into named policy functions.
  • Shadow-log old/new decision mismatches without changing enforcement.
2–3 weeks
Phase 3

Add modules and roles

  • Seed current roles as immutable system templates.
  • Migrate memberships to role assignments and preserve effective access exactly.
  • Add organization modules, custom-role UI, previews, and lockout protection.
3–4 weeks
Phase 4

Cut over and simplify

  • Require zero unexplained shadow mismatches.
  • Switch endpoints by module behind a reversible flag.
  • Remove legacy role branches only after route, UI, tenancy, and audit gates pass.
1–2 weeks
Separate identity checkpoint
Design sessions around membership_id now; lift the one-organization constraint later only if needed.

A multi-organization launch requires organization selection, safe tenant switching, host/cookie behavior, invite reuse, MFA/session semantics, support access, audit attribution, and cross-organization negative tests. It should not be bundled into the permission refactor by default.

08 / Acceptance gates

The upgrade is complete only when enforcement, UI behavior, and operational safety agree.

Tenant isolation

Every new access path has an explicit cross-organization denial test. No module, role, override, or external policy result can bypass membership-derived scope.

Policy coverage

Every protected API operation maps to a typed action; every contextual check has a named policy test; unknown actions deny by default.

Frontend parity

Navigation, route loading, prefetch, data queries, buttons, and denied states use the same surface manifest and are verified for each role fixture.

Change propagation

Permission and module mutations increment an authorization version, invalidate the acting admin’s queries, and cause affected clients to refresh on focus or the next denied response.

Safe administration

Admins see an impact preview, cannot remove the last role administrator, cannot grant a capability they cannot delegate, and cannot edit protected platform capabilities.

Auditability

Role, assignment, module, and override changes are atomic and audited. Decision telemetry stores identifiers, result, reason, and policy version without raw PII.

Migration parity

Current fixtures produce identical effective access under old and new evaluators before any endpoint cuts over. Every mismatch is dispositioned.

Failure posture

Protected API decisions fail closed. Frontend projection failures hide privileged controls and show a recoverable error; they never manufacture permissions.

Rollback

Each module can return to the legacy evaluator without reversing data migrations. New tables remain additive until the final cleanup release.

Boundaries to preserve

  • Do not treat frontend hiding as authorization.
  • Do not make tenant isolation, CSRF, MFA, human-review requirements, or developer/platform controls tenant-configurable.
  • Do not let organization admins create arbitrary permission keys or upload policy code; capabilities remain versioned application contracts.
  • Do not store raw PII or request bodies in decision logs.
  • Do not introduce OpenFGA, OPA, Cedar, or another service until a measured use case exceeds the in-process kernel.
09 / Research basis

Primary sources used to shape the options.

RBAC foundation
NIST — Role Based Access Control

Supports roles as the stable administrative layer connecting users to permissions, while recognizing hierarchical roles and constraints.

Authorization modeling
AWS Verified Permissions — Authorization Model Design

Frames authorization around principals, resources, actions, context, tenant strategy, UX queries, and lockout prevention.

Policy boundary
Open Policy Agent — Documentation

Separates policy decision-making from enforcement, the same seam proposed for the in-process kernel and a possible later external service.

Custom roles
OpenFGA — Modeling Roles

Compares static roles, organization-defined roles, and object-specific role assignments, including their increasing flexibility and complexity.

Domain modeling
OpenFGA — Authorization Model Design Principles

Recommends modeling the real domain instead of a generic authorization meta-model; this supports explicit modules, resources, and actions.

ReBAC scale trigger
Google Research — Zanzibar

Provides the relationship-based model behind external authorization systems; relevant when sharing graphs and service count outgrow local policies.

Typed policy schema
Cedar — Policy Validation

Treats the schema as a contract between application requests and policies, reinforcing generated action types and validation before enforcement.

Adoption pattern
OpenFGA — Adoption Patterns

Supports staged adoption and compatibility approaches rather than an all-at-once replacement of existing authorization checks.
